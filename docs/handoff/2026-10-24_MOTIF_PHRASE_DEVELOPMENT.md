# 코덱스 요청: 모티프와 프레이즈의 발전 — 단계별 작곡과 후보 비교 (2026-10-24)

## 0. 배경

사용자 판단(2026-10-24, 원문): "작곡은 아직 수준이 기대에 못 미치네요. 모티프와 프레이즈를 만들어서 발전시키는 과정이 부족하다고 느낍니다."

지금 방식은 다음과 같습니다.
- 작곡자(언어 모델)가 설계와 악보를 한 번에 써 내려갑니다.
- 프로그램은 변형 연산(이동, 뒤집기, 확대, 반복 진행)을 계산하고 검사합니다.

이 방식에서 빠진 것은 세 가지입니다.
1. **모티프를 고르는 단계가 없습니다.** 모티프가 정해지자마자 곡으로 갑니다. 리듬의 개성, 윤곽, 화성 방향이 약한 모티프는 변형해도 발전하는 느낌이 나지 않습니다.
2. **프레이즈 문법이 없습니다.** 설계가 구간 단위에서 멈춥니다. 문장형(기본 악상 → 반복 → 이어짐(조각내기·가속) → 종지)과 악절형(앞악구 반종지 → 뒷악구 정격종지)처럼, 각 자리의 기능과 그 기능에 맞는 발전 기법이 구조로 정해져 있지 않습니다.
3. **후보 비교가 없습니다.** 초안 하나로 끝납니다.

사용자가 승인한 진행 순서는 다음과 같습니다.
1. 단계별 작곡과 후보 비교(P1·P2)
2. 실제 곡의 발전 방식 통계(P3)
3. 기호 음악 모델 시험(P4)

선택 기록(P5)은 P1부터 함께 쌓습니다.

먼저 읽을 것: `AGENTS.md`, `docs/COMPOSING.md`, `musigen/motif.py`, `musigen/phrases.py`, `musigen/theme_metrics.py`, musicomp `musicomp/analysis/motif.py`, `musicomp/analysis/phrase.py`.

## 1. 작업 방식

- **브랜치**: 꾸러미마다 브랜치 하나와 검수 요청서 하나를 만듭니다.
  - `codex/motif-candidates`, `codex/phrase-grammar`, `codex/development-stats`, `codex/music-model-trial`
  - 검수 요청서는 `docs/handoff/review/YYYY-MM-DD_<주제>.md`에 씁니다.
  - origin/main에서 시작합니다. main에는 push하지 않습니다.
- **선택 기능**: 기존 `piece` 경로와 기존 예시 곡의 출력은 바꾸지 않습니다. `after_rain` 바이트 회귀 테스트가 계속 통과해야 합니다. 새 단계는 새 명령과 새 필드로 둡니다.
- **곡별 규칙 금지**: 예시 곡을 위한 분기를 만들지 않습니다.
- **기준값 근거**: 기준값에는 근거를 적습니다. 근거가 없으면 "잠정"이라고 적습니다.

- **자료 제한**
  - KYSing·AI Hub 자료는 쓰지 않습니다.
  - 저작권 악보에서 나온 원음 마디는 공개 저장소에 넣지 않습니다. 넣을 수 있는 것은 음정·리듬 유형 수준의 통계뿐이고, 출처와 라이선스를 함께 적습니다.
  - DCML은 비상업 조건이라 선택 옵션으로만 씁니다.
- **멈춤 기준**: 꾸러미마다 아래에 멈춤 조건을 두었습니다. 걸리면 반복 실험을 하지 말고 보고합니다. 보고에는 무엇이 한계인지, 어떤 자료가 더 필요한지를 적습니다.

## 3. P1 모티프 후보와 비교 페이지 (`codex/motif-candidates`)

### 3.1 후보 만들기

`python -m musigen motifs <작업 폴더> --count 8 [--seed N] [--include <모티프 JSON>...]`

- **입력**: `design.json`의 `basics`(박자, 조성, 빠르기, 급수), `impression`, 그리고 선택 필드 `theme.constraints`.
  - 예: `{"bars": 1, "range": "C4-A5", "start_on_beat": false, "rhythm": "syncopated"}`
- **후보의 출처**: 두 가지를 섞습니다. 각 후보에는 출처를 표시합니다.
  - 생성기: 리듬 세포 목록과 윤곽 유형(상행 도약 후 순차 하행, 아치, 같은 음 반복 후 도약 등)을 조합합니다. 화성 방향(으뜸→딸림, 으뜸 연장)을 정하고 강박 음을 그 화음에서 고릅니다.
  - 작곡자가 쓴 것: 대화 속 작곡자가 쓴 후보와, 모티프 작업실에서 가져온 JSON(`--include`)을 받습니다.
- **다양성 조건**: 후보끼리 리듬 지문(마디 안 시작 위치 집합)과 윤곽 유형이 겹치지 않게 합니다. 겹치는 후보는 버리고 다시 만듭니다. 최대 시도 횟수를 정해 둡니다.
- **후보마다 함께 내는 것**
  - 2마디짜리 맛보기: 모티프 + 기본 응답. 응답은 기존 연산으로 만듭니다(반복 진행 또는 리듬 유지 새 음).
  - 단순 반주: 블록 화음
  - 모티프 특징표: 음 수, 음역, 가장 큰 도약, 리듬 밀도, 당김음 여부, 화성 함의
- **출력**: `work/stage1_motifs/candidates.json`. 각 후보는 `musicanote-motif` v1 형식에 `id`, `origin`, `features`를 더합니다.

### 3.2 비교 페이지

- 후보를 한 화면에 나란히 둡니다. 각 후보에 악보 조각, 재생, 반복 재생, "이걸로" 버튼을 둡니다.
- 비교를 돕는 장치
  - 같은 빠르기와 같은 반주로 연속 재생합니다.
  - 두 후보를 고르면 번갈아 듣게 합니다.
- **선택 기록**: 정적 페이지(GitHub Pages)라 서버에 저장할 수 없습니다. 브라우저에 기억하고, "선택 내보내기"로 JSON을 받게 합니다. 받는 내용은 후보 id와 사용자가 적은 한 줄 이유(선택 사항)입니다.
- **선택 반영**: `python -m musigen choose <작업 폴더> <선택 JSON 또는 후보 id>`가 `selections.jsonl`에 기록하고, 다음 단계 입력을 만듭니다.

### 3.3 완료 기준과 멈춤

- 같은 설계로 8개 후보가 나와야 합니다.
  - 리듬 지문과 윤곽 유형이 모두 서로 달라야 합니다.
  - 모든 후보가 음역과 급수 조건을 만족해야 합니다.
- 비교 페이지: Verovio 오류 0, 모바일 390px에서 가로 넘침 없음, 선택 내보내기 동작.
- 시험 설계는 두 개입니다. 서정적 3/4 하나, 밝은 4/4 당김음 하나.
- **멈춤**: 다양성 조건을 만족하는 후보가 8개 중 6개 미만이면 멈춥니다. 생성기 규칙을 늘리지 말고, 어떤 리듬·윤곽 유형이 모자랐는지 보고합니다.

## 4. P2 프레이즈 문법과 후보 (`codex/phrase-grammar`)

### 4.1 문법

`score.json`에 새 재료 형식 `phrase`를 추가합니다. 기존 블록과 함께 쓸 수 있어야 합니다.

```json
{"bars": "1-8", "phrase": {
  "type": "sentence",
  "motif": "a",
  "harmony": "I I V V | IV V I",
  "functions": {
    "presentation": {"bars": [1, 4], "basic_idea": [1, 2], "repetition": "dominant"},
    "continuation": {"bars": [5, 6], "technique": ["fragment", "sequence:+1"], "harmonic_rhythm": "faster"},
    "cadential": {"bars": [7, 8], "cadence": "authentic", "technique": ["augment_end"]}
  },
  "accompaniment": {"presentation": "broken", "continuation": "block", "cadential": "bass"}
}}
```

- **지원할 유형**: 처음에는 세 가지입니다.
  - `sentence` (2+2+4)
  - `period` (앞악구 4 반종지 + 뒷악구 4 정격종지. 뒷악구는 앞악구 첫 2마디를 되풀이)
  - `hybrid` (앞악구 + 이어짐)
- **기능별 기본값**: 기능마다 쓰는 기법, 화성 리듬, 종지의 기본값을 표로 둡니다. 근거로 교과서 출처를 적습니다. 예: Caplin, *Classical Form*(1998)의 문장형·악절형 정의.
  - 이어짐(continuation): 조각내기, 반복 진행, 화성 리듬 가속. 단위가 짧아져야 합니다.
  - 종지(cadential): 종지 화음 진행. 선율은 종지음으로 정리합니다.
- **실현**: 프로그램이 오른손 선율 뼈대를 기존 `realise`와 `apply` 연산으로 만들고, 왼손은 기존 반주 음형으로 채웁니다. 작곡자가 마디별로 덮어쓸 수 있어야 합니다(기존 블록 재료로 덮어쓰기).

### 4.2 후보

`python -m musigen phrases <작업 폴더> --count 4`

- 선택된 모티프 하나로 프레이즈 후보 3–4개를 만듭니다.
- 후보끼리는 유형(문장형/악절형)이나 이어짐 기법(조각내기+반복 진행 / 리듬 축소 / 응답 확대)이 달라야 합니다.
- P1과 같은 비교 페이지와 선택 기록을 씁니다.

### 4.3 검사 추가 (참고 단계)

- **긴장 곡선**: 마디별로 선율 평균 음높이, 음 밀도, 화성 변화 수를 냅니다.
  - 이어짐 구간에서 밀도나 화성 리듬이 실제로 올라가는지 봅니다.
  - 설계 절정 마디가 곡선의 정점 근처에 있는지 봅니다.
- **기능 점검**
  - 이어짐 구간의 단위 길이가 앞 구간보다 짧아졌는지
  - 종지 마디의 화음과 선율 끝음이 지정한 종지와 맞는지
  - 뒷악구가 앞악구 첫 부분을 되풀이하는지
- 메시지는 한국어로 쓰고 마디 번호를 붙입니다. 기준값은 잠정입니다.

### 4.4 완료 기준과 멈춤

- P1 시험 설계 두 개의 선택 모티프로 각각 프레이즈 후보 4개를 만듭니다.
- 비교 페이지와 선택 기록이 동작해야 합니다.
- 문법 세 유형마다 단위 테스트를 둡니다: 마디 수, 기능 경계, 종지 화음.
- 고른 프레이즈로 기존 `piece`까지 이어 만든 16–24마디 곡 하나를 검수용으로 냅니다.
- **멈춤**: 문법만으로 만든 뼈대가 기계적으로 들린다고 판단되면, 기법을 더 붙이지 말고 P3·P4 결과를 기다립니다. 판단 근거는 작곡자의 자기 검토와 4.3의 검사 수치입니다.

## 6. P4 기호 음악 모델 시험 (`codex/music-model-trial`)

### 6.1 목적

"모티프와 화음 진행, 프레이즈 뼈대를 지키면서 이어지는 선율을 채우는" 공개 모델이 우리 규칙 생성기보다 나은 후보를 내는지 확인합니다. 기본 경로에 넣는 것은 이번 범위가 아닙니다.

### 6.2 후보 모델

- 1순위: Anticipatory Music Transformer(Stanford CRFM, 작은 모델). 주어진 사건을 고정하고 빈 곳을 채우는 기능이 있습니다.
- 다른 모델은 이유를 적고 하나까지만 시험합니다.
- 코드·가중치·학습 자료의 라이선스를 확인하고 적습니다.

### 6.3 시험

- 별도 가상환경에서 설치합니다. musicomp와 musigen의 환경을 오염시키지 않습니다.
- 개발 컴퓨터 GPU의 종류와 VRAM을 확인해 적습니다.
- 생성 조건: P2에서 고른 프레이즈의 기본 악상(1–2마디)과 화음을 고정하고, 나머지 6마디 선율을 16개 생성합니다.
- P2의 검사(기능 점검, 긴장 곡선)로 거른 뒤, 상위 4개를 규칙 생성 후보 4개와 같은 비교 페이지에 섞습니다.
  - 출처는 사용자 선택 뒤에 공개합니다(눈가림 비교).
- 보고 항목: 생성 시간, 메모리, 걸러진 비율과 이유, 사용자 선택 결과

### 6.4 멈춤

다음 중 하나라도 해당하면 멈추고 보고합니다.
- 설치와 실행 준비에 하루 이상 걸림
- GPU 메모리가 부족함
- 16개 중 박자·조성 조건을 지키는 후보가 4개 미만

## 7. P5 선택 기록

`work/selections.jsonl`에 한 줄에 한 건씩 남깁니다.

```json
{"time": "...", "stage": "motif|phrase|piece", "work": "<작업 폴더>", "shown": ["m1", "m2"],
 "chosen": "m3", "origin": {"m3": "generator|composer|import|model"}, "reason": "사용자 문장(선택)", "design_sha256": "..."}
```

- 출처는 사용자가 고른 뒤에 기록합니다. 눈가림 비교일 때 미리 보이지 않게 합니다.
- 이 기록은 나중에 후보 순위 기준을 조정하거나 모델을 조정하는 자료가 됩니다. 이번에는 쌓기만 하고 자동으로 학습에 쓰지 않습니다.

## 8. 사용자에게 받을 것

- **기준 곡**: 좋다고 느끼는 곡이나 직접 쓴 곡 몇 개(MusicXML 또는 모티프 작업실 JSON). 목표로 할 발전 방식의 예시로 씁니다. 저작권 곡은 로컬에만 둡니다.
- **선택 시간**: P1·P2 비교 페이지에서 고르는 일. 단계마다 몇 분이면 됩니다.

## 9. 검수 요청서에 넣을 것 (꾸러미마다)

- 무엇을 왜 바꿨는지, 바꾼 파일과 함수
- 테스트 수(전후)와 `after_rain` 회귀 결과
- 비교 페이지 경로. 사용자가 고를 곳은 후보 id와 마디로 적습니다.
- 기준값의 근거 또는 "잠정"
- 멈춤 조건에 걸렸는지, 한계와 필요한 자료
